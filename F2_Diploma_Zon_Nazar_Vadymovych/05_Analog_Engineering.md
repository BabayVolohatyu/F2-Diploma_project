# Інженерний опис аналогів

Для порівняння взято три системи, які вже працюють із даними закупівель або контрагентів: Prozorro Public API, DoZorro і YouControl.

## Prozorro Public API (OpenProcurement)

**Архітектурний патерн.** Операційна частина Prozorro — документний API. Публічний код OpenProcurement написаний на Python. Читання масштабується реплікацією документів, але клієнт забирає стрічку тендерів синхронним HTTP і впирається в ліміт частоти.

**Протокол.** Зовнішній обмін — REST/JSON. Документ тендера орієнтований на OCDS.

**Сховище і консистентність.** Основне сховище — CouchDB, пошук винесено в Elasticsearch. Аналітична вигрузка є окремою моделлю читання і відстає від операційного API. Документ узгоджується через MVCC у CouchDB, без спільної транзакції з чергою подій.

**Технічні обмеження.** Запит зв’язків бенефіціарів не є обходом графа. Синхронний прохід обривається на таймауті або відповіді 429. Скоринг ризику в сам API не входить.

## DoZorro

**Архітектурний патерн.** DoZorro (Transparency International Ukraine) — застосунок моніторингу поверх Prozorro Public API. Окремого брокера подій між збором і оцінкою немає.

**Протокол.** Дані тендерів читаються тим самим REST/JSON.

**Сховище і консистентність.** Внутрішню СУБД у публічному описі не названо. Власного графа контрагентів розрахунок ризику не зберігає.

**Технічні обмеження.** Ризик задано фіксованим списком індикаторів. Нова схема змови потребує нового правила. Скоринг чекає відповіді джерела. DREAM і ЄДЕССБ у цей розрахунок не входять.

## YouControl

**Архітектурний патерн.** Комерційне досьє контрагента з готовими зв’язками компаній. Це не обробник стрічки тендерів.

**Протокол.** Зовнішній контракт — REST/JSON з ключем і квотою запитів. Внутрішній протокол сервісів у публічній документації API не названий.

**Сховище і консистентність.** СУБД у публічній документації API не названа.

**Технічні обмеження.** Виклик API на кожен тендер додає Latency і зовнішню залежність. Немає стрічки закупівель, мапи відбудови і тендерного скорингу.

## Аналітичний висновок підрозділу 1.2

Синхронний REST у Prozorro Public API віддає тендер як документ CouchDB. Зв’язок бенефіціарів у цій моделі не рахується, а клієнт, який тягне стрічку в одному проході, зупиняється на ліміті частоти. DoZorro ставить поверх цього API фіксований список індикаторів. Оцінка ризику чекає відповіді джерела, а нова схема змови не з’являється в розрахунку, доки правило не дописано вручну. DREAM і ЄДЕССБ у цей розрахунок не входять.

YouControl віддає готові зв’язки компаній через REST з квотою. Це не стрічка тендерів і не мапа відбудови. Якщо викликати такий API на кожен лот, Latency скорингу складається із зовнішньої квоти, а не з часу власної моделі.

У кваліфікаційній роботі передбачено подієву обробку і CQRS. Запис тендера в PostgreSQL і публікація події в RabbitMQ узгоджуються через Transactional Outbox. HTTP-клієнти реєстрів закрито політиками Polly: retry, circuit breaker і rate limit. Повтор фонової задачі блокується в Redis. Афілійованість винесено в обхід графа Neo4j, скоринг аномалій — у ML.NET (Isolation Forest / gradient boosting). Ці рішення задають склад розділу 2: моделі UML і C4, схеми PostgreSQL, Neo4j і Redis, схему розгортання.
