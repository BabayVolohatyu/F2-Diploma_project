# Розділ 1. Аналіз предметної області та формування вимог

## 1.1 Актуальність теми та характеристика предметної області

Відбудова інфраструктури України супроводжується проведенням публічних закупівель, відомості про які формуються та публікуються в декількох інформаційних системах і державних реєстрах. Для аналітичного опрацювання використовуються Prozorro з моделлю даних OCDS, DREAM, ЄДЕССБ та відкриті набори data.gov.ua. Джерела відрізняються структурою документів, складом атрибутів, механізмами оновлення та обмеженнями інтерфейсів програмування. Побудова узгодженого набору даних потребує отримання записів, перевірки повноти, зіставлення ідентифікаторів, нормалізації та контролю повторного завантаження.

Предметна область охоплює аналіз закупівель, замовників, учасників, договорів, лотів, предметів закупівлі, об'єктів відбудови та контрагентів. Ознаки ризику можуть бути розподілені між різними записами. Окремий тендер може не містити достатньої інформації для висновку, тоді як повторювані зв'язки між учасниками, спільні ідентифікаційні атрибути або нетипова структура участі виявляються після зіставлення декількох джерел.

З інженерної точки зору ключовими напрямами є стандартизація відкритих даних, інтеграція через API, автоматизація ETL-процесів, застосування графових моделей для аналізу зв'язків та методів машинного навчання для ранжування підозрілих записів. Для таких систем важливі відтворюваність обробки, походження даних, стійкість до тимчасової недоступності зовнішніх сервісів і можливість пояснити фактори оцінки ризику.

## 1.2 Теоретичні та технологічні засади обробки даних закупівель

Інтеграція різнорідних реєстрів передбачає конвеєр Extract–Transform–Load (ETL). На етапі Extract отримуються записи через зовнішні API та завантажуються відкриті набори даних. На етапі Transform перевіряється структура відповіді, нормалізуються дати, суми й ідентифікатори, усуваються дублікати. На етапі Load нормалізовані об'єкти зберігаються у внутрішньому сховищі. Оскільки зовнішні джерела можуть повертати неповні сторінки, змінювати записи або обмежувати частоту запитів, процес має підтримувати повторне виконання та фіксацію стану синхронізації.

Для розділення операцій запису й читання доцільно застосувати Command Query Responsibility Segregation (CQRS). Команди змінюють стан доменних об'єктів, тоді як запити використовують моделі читання, оптимізовані для пошуку та аналітики. Подієво-керована взаємодія відокремлює отримання даних від нормалізації, побудови графа та розрахунку ризику. RabbitMQ може використовуватися як брокер внутрішніх повідомлень.

Під час запису об'єкта до PostgreSQL та створення повідомлення для RabbitMQ виникає проблема подвійного запису: збій між операціями може призвести до збереження даних без публікації події або до публікації події без відповідного стану в базі. Transactional Outbox усуває цю неузгодженість шляхом запису доменної зміни та outbox-повідомлення в межах однієї транзакції. Окремий процес публікує збережені повідомлення до брокера.

Для аналізу афілійованості реляційних таблиць може бути недостатньо, оскільки зв'язки між компаніями, бенефіціарами, контактними атрибутами та закупівлями мають мережеву структуру. Neo4j дає змогу представляти контрагентів як вузли, а відношення — як ребра, після чого виконувати пошук шляхів і спільних сусідів. PostgreSQL залишається основним транзакційним сховищем, а Neo4j використовується для графових запитів.

ML.NET передбачається для оцінювання аномальності та класифікації. Результат моделі є індикатором для пріоритизації перевірки, а не автоматичним доказом порушення. Для оцінки необхідно зберігати версію моделі, час розрахунку та доступні фактори. Зовнішні HTTP-виклики мають виконуватися з тайм-аутами, повторними спробами з обмеженням, circuit breaker та rate limiting; у проєкті ці політики передбачено реалізувати засобами Polly.

## 1.3 Аналіз існуючих аналогів

Для порівняння розглянуто Prozorro Public API (OpenProcurement), DoZorro та YouControl. Вони охоплюють різні частини предметної області: публікацію закупівельних даних, моніторинг індикаторів і надання відомостей про контрагентів.

### Prozorro Public API (OpenProcurement)

Операційна частина Prozorro надає дані закупівель через API у форматі, орієнтованому на OCDS. Зовнішня взаємодія здійснюється через REST/JSON. У наявному інженерному описі проєкту зазначено використання CouchDB для документного зберігання та Elasticsearch для пошуку. Така модель придатна для отримання документів закупівель, однак сама по собі не забезпечує спеціалізованого графа афілійованості або ML-оцінювання ризику.

Під час інтеграції зовнішній клієнт залежить від доступності API, пагінації та обмежень частоти запитів. Послідовний синхронний прохід може перерватися через затримку або HTTP 429. Споживачеві необхідно зберігати позицію синхронізації та повторювати запити відповідно до політики обмеження частоти.

### DoZorro

DoZorro є інструментом громадського моніторингу закупівель, що використовує дані Prozorro та набір індикаторів для виявлення потенційно проблемних закупівель. У доступному описі, використаному для цього аналізу, внутрішню СУБД і повну схему міжсервісної взаємодії не розкрито; тому конкретні технології зберігання або брокер повідомлень не приписуються системі без підтвердження.

Індикаторний підхід дозволяє формалізувати відомі сценарії ризику. Водночас нові комбінації ознак потребують окремого правила, якщо механізм не містить адаптивного або статистичного компонента. Для дипломного проєкту важливо доповнити правила аналізом зв'язків контрагентів і моделлю ранжування аномалій. У межах доступного опису не підтверджено інтеграцію DREAM та ЄДЕССБ у єдиний конвеєр аналізу.

### YouControl

YouControl надає інформацію про юридичних осіб та пов'язані з ними відомості, зокрема готові зв'язки між контрагентами. Зовнішній доступ до даних передбачає API з автентифікацією та обмеженнями використання. Внутрішня архітектура і СУБД сервісу не розкриваються у використаному публічному описі, тому їх не деталізовано.

Сервіс може бути джерелом додаткових відомостей про контрагентів, але не замінює конвеєр збору закупівельних даних, геопросторове відображення об'єктів відбудови та власну модель оцінювання ризику. Виклик зовнішнього API під час кожного розрахунку створює залежність від доступності та квоти постачальника. У цільовій системі зовнішні дані доцільно отримувати фоновими задачами, зберігати час актуальності та використовувати локальні моделі для повторного аналізу.

Проєктована система має інтегрувати ці функції в узгоджений процес з асинхронною обробкою.

## 1.4 Аналіз предметної області та процесів As-Is

### Актори та інформаційні сутності

Ключові актори:
- **Аналітик / аудитор закупівель** — переглядає закупівлі, аналізує фактори ризику, перевіряє зв'язки контрагентів і формує висновки.
- **Громадський спостерігач** — використовує відкриті відомості та результати моніторингу для визначення закупівель, що потребують уваги.
- **Оператор системи** — контролює синхронізацію джерел, фонові задачі, черги та помилки інтеграцій.
- **Зовнішні реєстри та API** — постачають первинні дані про закупівлі, об'єкти відбудови та контрагентів.
- **Адміністратор** — керує доступом, конфігурацією інтеграцій і параметрами обробки.

Основні сутності:
- **Закупівля (Tender)** — ідентифікатор, статус, замовник, дати, очікувана вартість і джерело.
- **Лот (Lot)** — частина закупівлі з предметом, сумою та статусом.
- **Учасник (Bidder)** — юридична особа або інший суб'єкт, що подав пропозицію.
- **Замовник (Buyer)** — організація, яка оголошує закупівлю.
- **Контрагент (Counterparty)** — юридична особа, щодо якої збираються реєстрові атрибути.
- **Зв'язок (Affiliation)** — типізоване відношення між контрагентами, наприклад спільний бенефіціар.
- **Об'єкт відбудови (ReconstructionObject)** — інфраструктурний об'єкт, пов'язаний із закупівлею та координатами.
- **Фактор ризику (RiskFactor)** — ознака, що впливає на оцінку закупівлі.
- **Оцінка ризику (RiskAssessment)** — результат розрахунку з рівнем, часом і версією алгоритму.
- **Джерело даних (DataSource)** — реєстр або API з датою синхронізації та статусом.

### Процес 1. Отримання та нормалізація закупівельних даних

У поточній моделі інтеграційний клієнт отримує записи із Prozorro та інших джерел через API або завантажує відкриті набори даних. Відповіді можуть містити пагінацію, різні формати дат, відмінні назви полів і посилання на пов'язані документи. Записи зіставляються за зовнішніми ідентифікаторами, перевіряються на дублювання та приводяться до спільної структури.

**Вузькі місця:** різні схеми потребують окремих адаптерів; послідовне опитування збільшує час збору; HTTP 429, тайм-аути або недоступність джерела переривають синхронізацію; без журналу стану складно визначити вже оброблені сторінки; повторний запуск без ідемпотентності може створити дублікати.

### Процес 2. Перевірка закупівлі та виявлення ризиків

Після отримання даних закупівля перевіряється за доступними атрибутами та індикаторами. Для поглибленої перевірки отримуються відомості про учасників і контрагентів, зіставляються з іншими записами та визначаються можливі зв'язки. У підходах, що спираються лише на фіксований перелік правил, результат залежить від попередньо описаних сценаріїв.

**Вузькі місця:** правило аналізує лише задану ознаку або комбінацію ознак; багаторівневі зв'язки важко виявити звичайними реляційними запитами; зовнішній запит до сервісу контрагентів додає затримку та залежність від квоти; відсутність версії моделі й факторів оцінювання ускладнює відтворення результату. Оцінка ризику не є доказом порушення без додаткової перевірки.

### Процес 3. Підготовка аналітичного результату та моніторинг

Після перевірки аналітик переглядає закупівлю, фактори ризику, відомості про контрагентів і пов'язані об'єкти. Результат використовується для пріоритизації ручної перевірки, формування звіту або відображення закупівель на карті. Для актуальності потрібні періодичне оновлення даних і контроль фонових процесів.

**Вузькі місця:** різні джерела мають різний час оновлення; ручне зведення відомостей збільшує час підготовки висновку; збій між збереженням результату та публікацією повідомлення може призвести до пропуску сповіщення; кілька екземплярів планувальника можуть запустити однакову задачу; без метрик складно оцінити затримку черги та частку помилок.

### Регуляторні та технологічні обмеження

Обробка закупівельних даних має враховувати умови використання відкритих API, ліцензії наборів даних, правила атрибуції та обмеження частоти запитів. Для обміну закупівельними даними важливо зберігати сумісність із OCDS там, де він застосовується. Дані юридичних і фізичних осіб мають оброблятися відповідно до законодавства України про захист персональних даних; публічність набору не скасовує необхідності мінімізувати обробку персональних даних і контролювати доступ.

Для вебзастосунку необхідно враховувати рекомендації OWASP щодо автентифікації, авторизації, валідації вхідних даних, керування секретами та захисту API. Секрети доступу до реєстрів не повинні зберігатися у вихідному коді. Для інтеграцій встановлюються тайм-аути, обмеження частоти, контрольовані повтори та журналювання помилок.

Опис As-Is фіксує проблеми інтеграції, синхронного виконання, дублювання задач, аналізу зв'язків і відтворюваності оцінок. Ці проблеми визначають вимоги до цільової моделі To-Be.

## 1.5 Постановка задачі та формування вимог

### Концептуальна модель To-Be

У цільовій моделі зовнішні джерела підключаються через окремі адаптери. Планувальник запускає збір даних, а HTTP-клієнти виконують запити з тайм-аутами, rate limiting, retry та circuit breaker через Polly. Документи проходять перевірку структури, нормалізацію та дедуплікацію. Для кожного запису зберігається ідентифікатор джерела, час отримання та стан обробки.

Нормалізовані закупівлі зберігаються у PostgreSQL. У межах тієї самої транзакції створюється запис Transactional Outbox. Publisher передає подію до RabbitMQ, після чого окремі обробники оновлюють граф Neo4j, розраховують ризик засобами ML.NET та оновлюють моделі читання. Такий поділ зменшує зв'язність етапів і дозволяє повторно обробити повідомлення після тимчасового збою.

Для запобігання паралельному запуску однакових задач застосовуються Redis locks із TTL та безпечним звільненням. Результат оцінювання зберігає рівень ризику, фактори, час і версію моделі. Angular-клієнт надає пошук, фільтрацію та геопросторове відображення закупівель і об'єктів відбудови. Сповіщення про події високого ризику передаються клієнтам через WebSockets.

### Функціональні вимоги (Core Features)

1. **Інтеграція джерел даних.** Отримувати закупівельні та реєстрові дані з Prozorro OCDS API, DREAM API, ЄДЕССБ і доступних наборів data.gov.ua через окремі адаптери.
2. **Нормалізація та дедуплікація.** Перевіряти структуру документів, приводити атрибути до внутрішньої доменної моделі та запобігати повторному створенню однакових записів.
3. **Асинхронна обробка подій.** Передавати внутрішні події через RabbitMQ, використовуючи Transactional Outbox для узгодження запису та публікації.
4. **Графовий аналіз контрагентів.** Зберігати підтверджені зв'язки у Neo4j та виконувати пошук спільних атрибутів і шляхів між вузлами.
5. **Оцінювання ризику.** Розраховувати оцінку за правилами та моделями ML.NET, зберігати рівень, фактори й версію алгоритму.
6. **Геопросторовий моніторинг.** Відображати закупівлі й об'єкти відбудови на інтерактивній карті з фільтрацією за регіоном, категорією та ризиком.
7. **Фонове планування та сповіщення.** Виконувати регулярні задачі через Quartz.NET або Hangfire, запобігати дублюванню через Redis locks та передавати сповіщення через WebSockets.
8. **Формування звітів і аудит.** Формувати PDF або JSON зі змістом закупівлі, факторами ризику, часом розрахунку, джерелами та версією моделі.

### Нефункціональні вимоги (NFRs)

Наведені значення є проєктними цільовими показниками для прототипу та мають бути перевірені навантажувальними й інтеграційними тестами. Це не твердження про вже виміряну продуктивність системи.

| ID | Категорія | Вимога та критерій приймання |
|---|---|---|
| NFR-01 | API Performance | Для 95% запитів читання внутрішнього API p95 ≤ 500 мс при 50 RPS і 50 одночасних сесіях на тестовому стенді. |
| NFR-02 | Ingestion Throughput | Конвеєр обробляє ≥ 10 нормалізованих документів/с за тестовим набором, без часу очікування зовнішнього API. |
| NFR-03 | Queue Processing | p95 від publish до підтвердження обробки ≤ 5 с для повідомлень до 64 KB за довжини черги до 1 000. |
| NFR-04 | Scalability | Перехід від 1 до 2 worker-ів забезпечує ≥ 1,5× приросту пропускної здатності на паралелізованому тестовому наборі. |
| NFR-05 | Reliability | Для 429, 5xx і тайм-аутів застосовуються обмежені retry/backoff та circuit breaker; повтор не створює дублікатів. |
| NFR-06 | Data Consistency | Доменна зміна та outbox-повідомлення записуються в одній транзакції PostgreSQL; кожна подія має унікальний ID для ідемпотентності. |
| NFR-07 | Security | Захищені API-операції вимагають автентифікації та рольової авторизації; передавання токенів — лише HTTPS/TLS 1.2+. |
| NFR-08 | Secrets Management | API-ключі, паролі й connection strings не зберігаються у Git, а надходять через змінні середовища або secrets середовища розгортання. |
| NFR-09 | Backup & Recovery | Backup PostgreSQL щонайменше раз на 24 год; цільові RPO ≤ 24 год і RTO ≤ 4 год для тестового середовища. |
| NFR-10 | Observability | Prometheus отримує метрики оброблених/невдалих повідомлень, довжини черг, тривалості імпорту та ML-оцінювання. |
| NFR-11 | Maintainability | Backend організовано за шарами Clean Architecture; build і tests виконуються в GitHub Actions для кожного PR. |
| NFR-12 | Security Scanning | CI виконує SonarQube та Trivy; критичні знахідки блокують quality gate відповідно до конфігурації проєкту. |

### Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка розподіленої інформаційно-аналітичної системи для автоматизованого збору, нормалізації та аналізу даних публічних закупівель у процесах відбудови інфраструктури України. Система має інтегрувати зовнішні реєстри, забезпечувати асинхронну обробку подій, транзакційну узгодженість через Transactional Outbox, графовий аналіз контрагентів і оцінювання ризиків засобами ML.NET, а також надавати геопросторове відображення та звітність. Досягнення визначених показників продуктивності, надійності й безпеки підлягає перевірці під час тестування.

## Висновки до розділу 1

У першому розділі розглянуто предметну область моніторингу публічних закупівель для відбудови інфраструктури та проаналізовано три рішення, що охоплюють різні частини процесу. Prozorro Public API забезпечує доступ до закупівельних документів, DoZorro реалізує моніторинг на основі індикаторів, а YouControl надає відомості про контрагентів і зв'язки між ними. У межах доступної документації цих рішень не підтверджено наявність єдиного конвеєра, який поєднує інтеграцію декількох реєстрів, графовий аналіз, ML-оцінювання та геопросторову аналітику.

Аналіз процесів As-Is дозволив локалізувати технічні обмеження: неоднорідність форматів зовнішніх джерел, обмеження частоти запитів, залежність синхронної обробки від доступності API, ризик неузгодженості між базою даних і брокером, дублювання фонових задач та складність виявлення багаторівневих зв'язків. Встановлено потребу зберігати походження даних, версію алгоритму й фактори оцінювання для відтворення результату.

Для усунення обмежень сформовано модель To-Be з адаптерами зовнішніх джерел, нормалізацією та дедуплікацією, асинхронною взаємодією через RabbitMQ, Transactional Outbox, PostgreSQL, Neo4j, Redis і ML.NET. Політики Polly мають забезпечувати контрольовану взаємодію із зовнішніми API, а Prometheus — спостережуваність конвеєра. Визначено вісім функціональних і дванадцять нефункціональних вимог. Числові показники NFR є цільовими параметрами прототипу та потребують експериментальної перевірки.

Отже, результати аналізу та формалізації вимог визначають основу для проєктування архітектури, моделей даних, компонентів інтеграції, черг повідомлень і механізмів оцінювання ризику. Деталізація цих рішень має бути виконана в розділі 2, а програмна реалізація та перевірка — у розділі 3 кваліфікаційної роботи.
